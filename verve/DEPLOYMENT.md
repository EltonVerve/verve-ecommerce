# Cash-on-delivery launch

The application has not been deployed. Hosting provider and domain are still needed.

## Admin operations

Order staff also have work queues for new orders, packing, deliveries and delivered orders awaiting cash; customer call/email links; printable packing slips; and internal handover notes. Notes are stored in the existing admin activity table and never shown in customer order tracking or packing slips. Repeated note submissions are deduplicated. These additions require no further database migration beyond `install_admin_tools.php`. Printing a slip does not change an order or confirm payment.

Before serving this update, run `php sql/install_admin_tools.php` after `php sql/install_order_operations.php`. The new migration is safe to rerun, preserves existing admins as owners, and has been applied to the local development database. Run it separately on the deployment database.

- **Low stock:** Admin > Low stock lists active products at or below the configurable threshold (default 5). The dashboard uses the same threshold. These are in-app alerts, not email notifications.
- **Returns:** Open an order and record received quantities, condition and reason. Only shipped/completed orders qualify. Restocking requires an explicit checkbox and resalable condition; damaged items never increase stock. Cumulative returns cannot exceed purchased quantities. Retried submissions cannot restock twice.
- **Refunds:** Owners record actual money returned, amount, reason and payment/receipt reference. Partial and full refunds are supported, capped at the order's confirmed collected total. Recording a refund does not transfer funds or restock goods. Old orders already marked refunded remain closed; no fictitious refund ledger entries are created for them.
- **Orders:** Search by order number, customer name/email/phone, delivery area, dates, delivery status and payment status. Results are paginated in groups of 25.
- **Staff access:** Owners can grant full owner access or restricted order-staff access to an existing account, or revoke admin access. Confirm changes with the acting owner's current password. Own-account access changes are blocked. Order staff can view orders, save delivery/payment collection status, assign riders and edit their own profile. Returns, refunds, catalogue management, reports, delivery prices and staff settings remain owner-only. Permissions are checked server-side on every admin request; revoked access takes effect on the next request. Staff use the existing password-based admin login and idle timeout.
- **Delivery assignment:** Each order can have a rider name/phone, reference and Nairobi dispatch time. Assignment does not automatically mark an order shipped. Closed orders retain read-only assignment details.
- **Admin activity:** Tracks product prices/stock, product visibility/deletion, delivery-area changes, order status/payment changes, received returns, refunds, assignments, thresholds and access changes, with the acting account and timestamp. Records are not editable through admin. Earlier activity is not reconstructed, and this is not a tamper-proof external audit service.

Run `php tests/admin_tools.php`, `php tests/admin_access.php` and `php tests/order_operations.php` on a test database. The access test also needs the local Apache site running and uses temporary accounts to verify real HTTP permissions and page rendering. Test fixtures are removed afterward.

## Delivery, payment and image management

Run `php sql/install_cbd_delivery.php` after the order-operations migration to apply the Oartis-style rates: Nairobi CBD always free, Nairobi KSh 400, outside Nairobi KSh 850, and free delivery from KSh 10,000 before discounts. This explicitly updates the named zones; other custom areas remain unchanged. Checkout updates its estimate while a customer types a town/city and the server independently calculates the fee. Unlisted towns use the Outside Nairobi rate. Nairobi neighbourhood customers should select Nairobi and put their estate/street in the address fields; this is not map-based geocoding. Edit area rates in Admin → Delivery areas.

Run `php sql/install_order_operations.php` before deploying this update. It installs delivery zones, payment state and order history. Nairobi is seeded at KSh 200, free from KSh 5,000 before discounts. These are proposed store prices, not verified courier quotes: review them in Admin → Delivery areas before launch. Customers select a delivery area; this is not geographic address verification. Admins must confirm the address is within that area before dispatch. Cart shipping is an estimate; checkout quotes the selected area.

Delivery advances pending → processing → shipped → completed (delivered). Pending/processing orders may be cancelled; stock is restored exactly once. Cancelled and delivered orders cannot be reopened. Received returns are reviewed separately, with optional explicit restocking of resalable goods. Payment is recorded separately as unpaid, collected, partially refunded or refunded. Refund records include amount and payment reference; they do not move money. Legacy orders keep their delivery status; only legacy `paid` orders are inferred collected, other legacy payment states require review. Legacy cancelled orders are not restocked retrospectively because their physical stock history is unknown. History begins with this update; earlier transitions are not reconstructed.

Product photos can be removed and reordered before saving. Enable PHP GD with WebP support in the web server's PHP configuration for automatic 600px/1600px optimization on upload. Without GD, originals remain usable and admins receive a notice. Uploads are limited to 5 MB and 12 megapixels each; total PHP request limits also apply. Unreferenced generated uploads and their variants are deleted after removal or failed saves. Seed images and shared referenced assets are retained. A hard process/server crash can still require manual orphan-file review.

## Performance setup

- Run `php sql/install_performance_indexes.php` once per database (safe to rerun). Back up first and schedule index creation off-peak on a large live database.
- Deploy `public/assets/products/optimized/` alongside the originals. Run `php sql/optimize_images.php` with GD/WebP enabled after adding or replacing product photos; XAMPP CLI can use `php -d extension=gd sql/optimize_images.php`. Conversion runs offline, never during a shopper's request. Missing or older variants fall back to the original image. Preserve modification times when uploading, or regenerate on the server.
- Apache asset caching/compression is configured in `public/assets/.htaccess` when the corresponding modules and overrides are enabled. Configure equivalent rules on other servers. Account/cart HTML stays private and uncached. Replacing an image with the same filename can leave a cached copy for seven days; prefer new upload filenames.
- Enable PHP OPcache in the host configuration and monitor PHP worker capacity, query latency and slow-query logs. Verify these settings on the actual host; they cannot be enabled reliably by this repository alone.
- Catalogue pages contain 24 products with filters preserved between pages. Related products use newest-first ordering instead of random database sorting. Text search still uses substring matching to preserve existing behavior; consider full-text search after measuring large-catalogue workloads.
- Test with `php tests/catalogue_performance.php`. Compare mobile page-load measurements on the deployment host; smaller assets are not a measured guarantee of a particular loading time. Mail delivery remains synchronous until a worker/queue is configured.

## Customer email-first sign-in

Run `php sql/install_customer_login_codes.php` before enabling email-code login. Without `VERVE_MAIL_FROM`, customers enter their email, then their existing password. Once a verified sending address and working PHP mail transport are configured, the default becomes email followed by a six-digit code. Test delivery with a real mailbox before enabling it publicly; a configured address alone does not prove delivery. Existing password login remains available as a fallback. Registration and profile password requirements are unchanged.

Codes expire after 10 minutes, allow five guesses, are stored as password hashes, are bound to the requesting browser session, and are consumed atomically. Resending replaces that browser's previous code. Send and verification endpoints have database rate limits; account existence is not disclosed in the response. Codes are never printed or logged. Admin login remains password-based.

Customer logins persist across browser restarts for 30 days of inactivity, renewed on each visit and enforced by both the database and cookie. Logout and password changes invalidate remembered logins. Admins must sign in again after 30 minutes of inactivity. Current passwords remain required for profile edits.

When upgrading, run `php sql/install_customer_sessions.php` before serving the updated application. This idempotent migration adds server-side expiry. Existing remembered logins without an expiry and existing admin sessions without an activity timestamp require one fresh sign-in.

1. Use a supported PHP release with PDO MySQL, mbstring and fileinfo, MySQL/MariaDB, and HTTPS. Point the domain document root at `verve/`, not the repository root. On Apache enable `.htaccess` overrides for these access rules. On Nginx configure equivalent deny rules for config, includes, models, sql, tests, dotfiles and executable files in uploads; Apache rules do not apply to Nginx.
2. Back up the database and uploaded products before deployment; test a restore. Import a clean schema for a new store or migrate the existing database without re-importing the schema. Run `php sql/install_customer_sessions.php` if needed and `php sql/install_auth_rate_limits.php`. The latter is required for login and profile saves. Existing reset links issued before this change must be requested again.
3. Configure server environment variables: `VERVE_ENV=production`, `VERVE_BASE_URL=https://your-domain.example` (include any installation subdirectory), `VERVE_DB_HOST`, `VERVE_DB_NAME`, `VERVE_DB_USER`, and `VERVE_DB_PASS`. Use a dedicated database account restricted to this database; no root account. Supply migration privileges only while migrating. Production uses `config/database.production.php`; local development retains `config/database.php`.
4. Configure TLS at the application server. If using a trusted reverse proxy, configure the server to set HTTPS correctly; the application deliberately does not trust arbitrary forwarded headers. Verify HTTP is redirected to HTTPS by the web server before it reaches PHP.
5. Replace the seeded admin password through Admin → My profile. Remove demo accounts and orders from the production dataset. Keep credentials outside the repository. Make only `public/assets/products/` and the PHP session directory writable by the web process, and keep session files and error logs outside the document root.
6. Set `VERVE_MAIL_FROM` to your verified sending address and configure the host's PHP mail transport (authenticated SMTP relay). Test password recovery delivery, expiry, and reuse. Reset links are never exposed in the browser or logs. Until mail delivery is configured, recovery cannot deliver email. Order confirmation emails are not implemented.
7. Checkout accepts cash on delivery only. Orders start pending; admins update fulfillment/payment status after actual collection. Set real shipping fees and delivery coverage, verify stock and prices, publish contact details and return/privacy policies, and arrange fulfillment and cash collection before accepting orders.
8. Run `php tests/customer_session.php` and `php tests/customer_activity.php` against a test database. They roll back their test records. Test customer registration, login, profile updates, admin profile updates, customer activity, wishlist, checkout, and order ownership in a browser. Verify unauthenticated admin access redirects and config/schema/test URLs return 403/404. Verify uploaded scripts cannot execute. Test password recovery using a real mailbox.
9. Set up automated backups, error monitoring, host updates and uptime checks. Apply host-level abuse limits to checkout, registration and public forms. Login, password recovery and profile password checks have database-backed 15-minute rate limits; this is not a complete security audit or a substitute for host configuration.

Customer activity shows join date, order history, current wishlist/cart and reviews. Each section displays the latest 100 records. It does not track browsing or reconstruct removed wishlist/cart items. Profile editing is self-service: admins edit their own profile, customers edit their own profile.
